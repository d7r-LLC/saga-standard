Architecture Approaches

How should the SAGA App be structured internally?

A

Feature-Module Architecture (Recommended)

Organize by domain feature modules, each self-contained with screens, hooks, state, and services. Inspired by BlueWallet's class hierarchy but with modern Expo patterns.

Project Structure
saga-app/
├── app/                    # Expo Router (file-based routing)
│   ├── (tabs)/             # Tab navigator
│   │   ├── wallet/         # Wallet tab screens
│   │   ├── directory/      # Directory browse/search
│   │   ├── messages/       # DMs, groups, sync
│   │   ├── documents/      # SAGA document explorer
│   │   └── settings/       # Profile, security, chain ops
│   ├── (auth)/             # Auth flow (onboarding wizard)
│   └── (modals)/           # Full-screen modals (send, mint, etc.)
│
├── features/               # Domain feature modules
│   ├── wallet/             # Wallet management
│   │   ├── hooks/          # useWallet, useBalance, useTx
│   │   ├── services/       # WalletService, KeychainService
│   │   ├── components/     # WalletCard, TxList, FundingFlow
│   │   └── types.ts
│   ├── identity/           # On-chain identity (NFTs, handles, TBAs)
│   │   ├── hooks/          # useIdentity, useHandle, useMint
│   │   ├── services/       # ChainService, RegistryService
│   │   ├── components/     # IdentityCard, MintWizard
│   │   └── types.ts
│   ├── messaging/          # Relay, DMs, groups
│   │   ├── hooks/          # useRelay, useMessages, useGroups
│   │   ├── services/       # RelayService, EnvelopeService
│   │   ├── components/     # ChatView, GroupList, MessageBubble
│   │   └── types.ts
│   ├── documents/          # SAGA document management
│   │   ├── hooks/          # useDocuments, useTransfer
│   │   ├── services/       # DocumentService, ExportService
│   │   ├── components/     # DocExplorer, LayerViewer
│   │   └── types.ts
│   ├── directory/          # Agent/org browsing & search
│   │   ├── hooks/          # useSearch, useResolve
│   │   ├── services/       # DirectoryService
│   │   └── components/     # AgentCard, OrgCard, SearchBar
│   ├── payments/           # x402 payment client
│   │   ├── hooks/          # usePayment, useSubscription
│   │   ├── services/       # X402Client, SubscriptionService
│   │   └── components/     # PaymentSheet, PlanSelector
│   └── governance/         # Org policies & audit
│       ├── hooks/          # usePolicy, useAuditLog
│       └── components/     # PolicyEditor, AuditTrail
│
├── core/                   # Shared infrastructure
│   ├── providers/          # StorageProvider, AuthProvider, ChainProvider
│   ├── crypto/             # saga-crypto integration
│   ├── chain/              # viem client, contract configs
│   ├── storage/            # Encrypted local storage (Realm/MMKV)
│   └── theme/              # Design system, colors, typography
│
└── packages/ (existing)    # @d7r/saga-sdk, saga-crypto, saga-client-rt

Pros

  • Each feature is independently testable
  • Clear ownership boundaries for parallel development
  • Features can lazy-load for performance
  • Follows Expo Router conventions

Cons

  • More boilerplate upfront
  • Cross-feature coordination needs careful design
B

BlueWallet Clone Architecture

Mirror BlueWallet's structure directly — class-based domain models, Context providers for state, screen-organized navigation. Proven pattern from a production crypto app.

Project Structure
saga-app/
├── class/                  # Domain model classes
│   ├── wallets/            # AbstractWallet → ManagedWallet, SelfCustodyWallet
│   ├── identities/         # AbstractIdentity → AgentIdentity, OrgIdentity
│   ├── saga-app.ts         # Singleton app state manager
│   └── relay-client.ts     # WebSocket relay connection
│
├── components/             # All UI components (flat)
│   ├── Context/            # StorageProvider, IdentityProvider, RelayProvider
│   ├── themes/             # Theme definitions
│   └── *.tsx               # Reusable UI components
│
├── screen/                 # All screens organized by feature
│   ├── wallets/            # Wallet screens
│   ├── identity/           # Identity management screens
│   ├── messages/           # Messaging screens
│   ├── documents/          # Document screens
│   ├── directory/          # Directory browse screens
│   └── settings/           # Settings screens
│
├── navigation/             # React Navigation setup
│   ├── index.tsx           # Root navigator
│   ├── DrawerRoot.tsx      # Drawer navigation
│   └── *Stack.tsx          # Feature stacks
│
├── hooks/                  # Custom hooks (flat)
├── models/                 # Data types
├── blue_modules/           # Utility modules (API clients, encryption)
└── loc/                    # Localization

Pros

  • Battle-tested in production crypto app
  • Class-based models are easy to reason about
  • Direct reference for patterns & solutions

Cons

  • Singleton pattern limits testability
  • Flat component/hook dirs don't scale well
  • Not idiomatic Expo Router (uses React Navigation directly)
  • Older patterns — no file-based routing
C

SDK-Driven Thin Shell

Maximize reuse of existing SAGA packages. The app is a thin UI shell that wires up saga-client-rt, saga-sdk, and saga-crypto. Minimal custom business logic — the SDK IS the app logic.

Project Structure
saga-app/
├── app/                    # Expo Router screens (thin)
│   ├── (tabs)/
│   └── (modals)/
│
├── ui/                     # Pure UI components
│   ├── chat/               # Message rendering
│   ├── wallet/             # Balance, tx display
│   ├── forms/              # Input components
│   └── shared/             # Design system
│
├── providers/              # Wiring SDK → React
│   ├── SagaProvider.tsx    # Creates & manages SagaClient instance
│   ├── WalletProvider.tsx  # Wallet abstraction
│   ├── ChainProvider.tsx   # viem/wagmi chain connection
│   └── PaymentProvider.tsx # x402 payment state
│
├── hooks/                  # Thin hooks wrapping SDK methods
│   ├── useSagaClient.ts    # Access SagaClient from context
│   ├── useMessages.ts      # client.onMessage() → React state
│   └── useDocuments.ts     # client.storeMemory() wrappers
│
└── @epicdm/ packages       # ALL business logic lives here
    ├── saga-client-rt       # Relay, messaging, memory
    ├── saga-sdk             # Documents, validation, encryption
    ├── saga-crypto          # Keys, envelopes, key ring
    └── saga-client          # REST API + chain ops

Pros

  • Maximum code reuse from existing packages
  • App stays lightweight and focused on UX
  • SDK improvements automatically benefit app

Cons

  • SDK APIs may not map cleanly to mobile UX needs
  • App-specific state (navigation, UI state) still needs a home
  • SDK changes can break app unexpectedly
  • May need SDK extensions that don't belong in the SDK
